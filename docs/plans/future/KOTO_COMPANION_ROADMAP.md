# Koto 浮窗助手跨平台里程碑

版本日期：2026 年 10 月 14 日，Asia/Shanghai。状态：规划草案，开发与产品验收尚未开始。

新版 Koto 是伴随 Office 和 WPS 的桌面 AI 浮窗，提供对话、多文件任务、逐段反馈和文件交付。文档始终由 Office 或 WPS 编辑、计算和渲染。Windows 与 macOS 共用任务协议与交互规则，分别实现原生应用连接、文件访问和系统拖放。

最终目标是 Windows Office、Windows WPS、Mac Office、Mac WPS 四个组合均能完成共同的核心流程。旧 Koto 仅作为场景和交互参考；新 Agent 的运行时、状态模型、执行器和验收测试独立设计。

配套的[验收方案](KOTO_COMPANION_ACCEPTANCE.md)定义用例、测量口径、证据和放行标准。完成代码、演示动画或模拟连接器均不等于完成真实桌面验收。

## 产品交付范围

第一版的核心流程是：在原生应用中编辑，用户逐段检查并改变方向，保存对应版本，再从浮窗把一个或多个文件拖入微信等目标应用。

| 能力 | 第一版交付要求 |
| --- | --- |
| 浮窗 | 收起、展开、拖动、跨屏移动；明确当前查看文件与任务修改目标 |
| 自有 API | 自定义接口地址、密钥、模型，连接检查、能力识别、费用与错误状态 |
| 文件托盘 | 正在编辑、本次任务、待交付三组；支持拖入、多选、定位、另存为后的关联更新 |
| 原生编辑 | Word 或 WPS 文字的选区、段落、基础表格操作；Excel 或 WPS 表格的指定区域与公式操作 |
| 人机协作 | 每个可判断的成果可保留、重做、撤销、暂停、追加任务或改变后续方向 |
| 恢复 | 记录实际完成的动作，恢复前重新核实文档；结果不明的动作单独处理 |
| 文件交付 | 手动保存后直接拖出；未保存时保存并准备交付；交付副本固定版本 |
| 跨应用成果 | 支持将已核验的内容放入原生演示文稿；先实现明确支持的内容和版式 |

v1 不把全自动选择联系人并发送消息作为必需功能。用户将文件拖进微信后，由目标应用处理附件和发送；收到拖放回调不能被报告为消息已发送。后续自动发送应另设里程碑，定义收件人绑定、授权和结果核验。

## 平台支持矩阵

| 配置 | 首发验证基线 | 最终共同要求 | 当前规划状态 |
| --- | --- | --- | --- |
| P1 | Windows 11 x64 与 Microsoft 365 桌面版 | 文字、表格、演示文稿的约定操作及文件交付 | M0 待验证 |
| P2 | Windows 11 x64 与 WPS 桌面版 | 同上，明确个人版或企业版等发行渠道 | M0 待验证 |
| P3 | Apple Silicon Mac 与 Microsoft 365 桌面版 | 同上，覆盖选定的两个受支持 macOS 版本 | M0 待验证 |
| P4 | Apple Silicon Mac 与 WPS 桌面版 | 同上，原生连接路线单独验证 | M0 待验证，主要技术风险 |

M0 冻结每个配置的 OS 版本与 build、CPU 架构、办公客户端版本与渠道、微信版本、桥接运行时及安装方式。Mac 的两个 OS 版本必须处于选定办公客户端的支持范围内。Windows ARM64、Mac Intel 和其他永久授权 Office 版本作为扩展兼容项逐项决定，不自动计入首发基线。

Microsoft 的 Office Add-ins 支持跨平台，但具体 API 受宿主、版本和 requirement set 限制；COM/VSTO 仅适用于 Windows。因此共同协议应以能力声明为边界，Windows 专用实现留在适配层。[Office 平台概述](https://learn.microsoft.com/en-us/office/dev/add-ins/overview/office-add-ins)、[Office 平台与 API 可用性](https://learn.microsoft.com/en-us/javascript/api/requirement-sets)。

WPS 当前公开的加载项概述明确列出 Windows/Linux，不能据此推定 Mac WPS 提供相同接口。P4 必须验证实际版本上的官方加载项、可用脚本或其他原生自动化能力，以及实际可持续安装的桥接方式。[WPS 加载项概述](https://open.wps.cn/documents/app-integration-dev/wps365/client/wpsoffice/wps-integration-mode/wps-addin-development/addin-overview)。

如果 P4 无法覆盖核心操作，相关阶段保持阻塞，并记录缺失能力及供应商依赖。其他组合可继续开发，但不能把手工导出、只读预览或从磁盘覆盖已打开文档记为 P4 原生编辑通过。调整最终支持范围须经用户明确同意。

## 实施边界

### 共用的产品与 Agent 层

浮窗交互、任务协议、模型接入、目标绑定、计划版本、变更记录、反馈、持久化进度和交付记录共用。新核心不依赖旧 Koto 的 Agent、路由、分类器或执行循环。

自然语言交给新 Agent 处理；保存、定位和拖出等明确按钮直接调用原生操作服务。模型断网或未配置时，已具备权限的文件操作仍然可用。共用层不使用盘符、COM 对象、Apple Event 对象或特定宿主的窗口句柄。

Agent 执行链路为：读取实际状态，规划小步操作，校验目标与计划版本，执行原生动作，读回验证，记录成果，等待或接收用户反馈。同一文档的写入有序执行；读取独立材料可以并行。反馈检查点与权限审批是不同概念，用户不必为每个底层工具调用重复确认。

### 各平台的原生层

| 工作 | Windows | macOS |
| --- | --- | --- |
| 桌面壳 | 原生窗口、托盘、跨屏、焦点与手势 | 原生窗口、菜单栏、Spaces 与全屏应用行为 |
| Office | 优先验证 Office.js 共同能力；COM/VSTO 可作为本端能力补充 | Office.js 为候选；原生自动化按实际宿主支持验证 |
| WPS | 官方加载项或实际版本支持的接口 | M0 独立验证，不复用 Windows 的能力假设 |
| 拖放 | Shell/OLE 文件拖放，例如 CF_HDROP | AppKit 拖放与文件 URL；按目标应用验证数据格式 |
| 文件权限 | 用户选择路径、目录权限和不同权限等级进程的行为 | 用户选择路径、所需的文件授权；使用沙盒时验证书签访问 |
| 密钥 | 系统凭据保管服务 | Keychain |
| 分发 | 带签名的安装包与升级路径 | Developer ID 签名、公证及正常 Gatekeeper 启动 |

桌面壳选型在 M0 同时通过两端真实文件拖出、原生桥接和分发实验后确定。不能只依据前端复用率选择技术栈。浏览器拖拽动画不是系统文件拖放；Office 内桥接的生命周期也不能假设为浮窗生命周期。

Windows 已有文件通过 Shell 文件数据格式交付；macOS 通过 AppKit 拖放会话交付。两者共享文件身份和交付版本语义，不共享系统拖放实现。[Windows Shell 数据传输](https://learn.microsoft.com/en-us/windows/win32/shell/datascenarios)、[AppKit Drag and Drop](https://developer.apple.com/documentation/appkit/drag-and-drop)。

### 运行时选型

M0 以 LangGraph 加办公专用工具作为首选验证路线，以 Pi 的轻量循环作为对照，核对锁定版本、许可证和模型兼容性。评估 OpenCode 的服务与界面分离、OpenHands 的动作与观察建模、Deep Agents 的上下文与工具装配。只选择一条主执行链，避免同时嵌套多个 Agent 运行时。

Pi Durable 在当前官方文档中标为实验性，须单独评估升级与恢复风险；对话持久化不等于外部应用动作可无条件重放。[Pi Durable](https://github.com/earendil-works/pi/blob/v1.2.0/packages/durable/README.md)、[Deep Agents 架构](https://github.com/langchain-ai/deepagents/blob/deepagents%3D%3D0.7.25/libs/ARCHITECTURE.md)、[OpenCode 服务](https://opencode.ai/docs/server/)、[OpenHands 架构](https://docs.openhands.dev/sdk/arch/overview)。

### M0 平台与运行时验证

交付四组合的能力记录、可重复的最小实验、候选桌面壳比较和运行时决策。逐一验证：识别目标文档、读取选区、替换一段、确认原生显示、保存完成、取得可交付文件、向真实微信发起文件拖放。

必须同时验证两个 Office 窗口、同名文件、桥接面板收起或关闭、宿主重启、浮窗失焦以及办公客户端与本地引擎之间的实际通信。Office WebView 需要的 HTTPS、证书、来源校验、端口与本地网络限制均在此阶段验证。

放行用例：CAP-01 至 CAP-04、DOC-01、FILE-01、DRAG-01。每个拟承诺的宿主组合均须有演示录像和版本记录。若 P4 未通过，M0 标为部分完成，P4 保持阻塞；共用组件可继续，不宣称四组合可行性已完成。

### M1 共用协议与新引擎

交付独立的新核心、适配器协议、事件流、操作记录、模型能力配置和操作模拟器。协议至少覆盖任务、计划版本、文档会话、定位锚点、动作身份、执行证据、交付副本和结果不明状态。

检查点分别保存任务进度与操作证据。重启后先重新绑定宿主并检查实际内容，再决定续做；对外部副作用不宣称通用的恰好一次执行。支持能力探测，宿主不具备的工具不对模型虚假开放。长对话压缩与模型切换不能丢失文件范围、用户已认可内容、反馈方向和待执行动作的约束。

放行用例：HAR-01 至 HAR-06。所有共用核心验证能在两个 OS 上运行；模型支持以能力配置决定，不依赖模型名字猜测可用工具。

### M2 浮窗与文件交付

交付可收起与展开的浮窗和三组文件托盘。当前文档显示所属应用、保存状态、来源位置和任务角色。保存、定位、准备交付和发起拖放通过明确按钮走原生服务，无需等待模型。

已保存文件可直接拖出；有未保存修改时提供保存并准备拖出。新建文档调用宿主的另存为流程。交付副本固定保存版本，随后源文档继续编辑不会改变该次交付。副本生命周期覆盖目标应用延迟读取和应用重启，取消拖放也不会移动或删除源文件。

放行用例：SHELF-01 至 SHELF-04、FILE-01 至 FILE-06、DRAG-01 至 DRAG-05。Windows 与 Mac 各完成 Office 的完整真实流程；WPS 按独立配置验收，其失败不能由 Office 的成功代替。

### M3 原生文档编辑

交付原生选区和段落读写、基础表格编辑、修改定位、单步变更记录及目标绑定。Word/WPS 的画布是最终显示依据，浮窗不建设第二套可编辑文档画布。

明确支持的文档结构并逐项验收。正文、段落样式、编号、表格、图片、页眉页脚和修订等既有结构在无关区域必须保留；不支持的目标结构提示无法处理。相同宿主内验证格式和内容保留，跨 Office/WPS 的排版不以像素完全一致为目标。

放行用例：DOC-01 至 DOC-05。连接中断、只读和用户并发修改均不得被伪报为写入成功。

### M4 反馈与恢复

交付成果检查点、保留继续、重做本段、改后续方向、追加任务、暂停和选择性撤销。用户明确改变方向后，立即停止派发旧计划的新写入；已经执行中的原子动作据实显示为等待完成或待核实。

撤销针对已记录的 AI 操作。用户后续在相同位置编辑造成冲突时，展示合并或重做方案，不能以整文件回滚覆盖用户内容。退出检查点和恢复任务时分别验证 UI、核心、桥接进程和宿主进程的状态。

放行用例：CTRL-01 至 CTRL-05、REC-01 至 REC-04；验证模型调用故障、写入中断及交付结果不明的独立处理。

### M5 多文件与表格任务

交付参考材料与修改目标的分组、选定文件批量处理、来源定位、数值核验和结果过期标记。Excel/WPS 表格通过原生对象操作指定区域和公式，由宿主重算。

验证多份表格汇总为报告、两份报告一致性修改，以及来源更新后只重做受影响部分。已认可成果依赖变化时标为待复核，不静默覆盖。PDF 在这一阶段作为材料读取和定位，PDF 自身的完整编辑不计入共同核心范围。

放行用例：MULTI-01 至 MULTI-03、SHELF-04、DOC-03、CTRL-02。

### M6 跨应用成果

交付将报告中的已认可内容放入 PowerPoint/WPS 演示的受支持对象、批量文件交付和版本历史。输出应能在原生应用内继续编辑；对来源和输出保留关联，不承诺目标应用没有接口时也能持续同步。

目标接收附件、用户实际发送和消息送达是不同事实。第一版的共同要求是原生文件拖放与可验证附件接收；发送与送达只在存在独立证据时记录。

放行用例：MULTI-04、DRAG-01 至 DRAG-05、REC-03；两个平台各自验证微信以及本地文件管理器等第二个目标。

### M7 跨平台发布候选

交付正式方式安装的候选包、宿主插件部署、权限管理、升级与回退、平台能力清单和脱敏诊断。Windows 验证不同完整性等级下的拖放结果；Mac 验证授权拒绝与撤销、文件访问、全屏、Spaces、多显示器及签名公证。

Mac 首发暂按 Developer ID 分发验证。Mac App Store 分发另行评估沙盒与插件部署约束，不用开发者模式或关闭系统保护代替正式安装验收。[Developer ID](https://developer.apple.com/developer-id/)、[macOS 软件公证](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)。

放行用例：PLAT-01 至 PLAT-06、PKG-01 至 PKG-03、PERF-01 至 PERF-03。所有声明支持的配置必须用实际安装包完成测试。

### M8 真实用户试用与首发

建议至少 10 名试用者，其中 Windows 与 Mac 各至少 5 名；每人完成至少 5 个约定任务，共至少 50 个真实任务。任务包含逐段修改、改方向、多文件汇总、保存交付和恢复。每个宿主组合均须有真实用户任务，Office 不能替代 WPS 的覆盖。

放行用例：PILOT-01 及全量核心回归。每个 P1 至 P4 配置及其冻结 OS 子配置完成 20 次完整核心流程，正确版本交付、目标绑定、内容保留和不重复副作用全部通过。试用任务成功率至少 95%，关键用例必须 100% 通过，未解决的 S0/S1 缺陷为零。

20 次核心流程是当次发布的验收批次，不代表长期可靠性上限。失败后修复并重新执行对应批次，失败记录保留。若 P4 仍阻塞，四组合最终里程碑不通过。

| 四组合办公客户端及可持续安装方式 | M0 | 记录 API 与部署限制；对应宿主工作线阻塞 |

开发负责人提交实现与操作证据，测试负责人执行验收，产品负责人确认成果粒度与用户体验。角色在项目启动时分配给实际成员。阶段状态只有未开始、进行中、阻塞、待验收、已验收五种；已验收必须关联具体版本和测试记录。

平台能力受限时，阻塞项至少包含宿主版本、失败动作、所需能力、替代路线、下一次验证条件和责任角色。回退路线仍须满足同一成果要求；单纯减少用例不能视为风险已解决。

## 最终完成条件

最终完成要求四个组合都能以正式安装方式运行，共同核心功能通过同一语义的测试。两端允许使用不同连接器、原生拖放实现与权限流程。所有支持版本均有清单，文档格式、来源关系、交付版本与任务恢复均有可检查的证据。

最终发布包必须附带验收汇总、已知限制、平台能力表、升级回退说明、真实用户试用结果和版本化用例记录。详细判定以[验收方案](KOTO_COMPANION_ACCEPTANCE.md)为准。
