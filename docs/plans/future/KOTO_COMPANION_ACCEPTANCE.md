# Koto 浮窗助手跨平台验收方案

版本日期：2026 年 10 月 14 日，Asia/Shanghai。状态：规划草案。下列用例的初始执行状态均为 NOT_RUN，尚无产品通过结论。

本方案验证 Windows 与 macOS 上的真实办公协作，包括原生编辑、逐段反馈、多文件管理、保存、系统拖放和故障恢复。配套的[里程碑路线图](KOTO_COMPANION_ROADMAP.md)规定 M0 至 M8 的交付顺序。验收以原生应用和实际文件为依据，模型回答“已完成”不能作为操作成功证据。

## 验收范围和配置

### 平台配置

| 配置 | 操作系统与宿主 | 需要真实测试的接收端 |
| --- | --- | --- |
| P1 | Windows 11 x64，选定版本的 Microsoft 365 Word、Excel、PowerPoint | Windows 微信与文件资源管理器 |
| P2 | Windows 11 x64，选定版本和渠道的 WPS 文字、表格、演示 | Windows 微信与文件资源管理器 |
| P3 | Apple Silicon，两个选定且受宿主支持的 macOS 版本，Microsoft 365 | Mac 微信与 Finder |
| P4 | Apple Silicon，两个选定且受宿主支持的 macOS 版本，WPS | Mac 微信与 Finder |

每个 P 配置与每个选定 OS 版本形成独立环境单元。P3 和 P4 各至少有两个 OS 子配置；相同 CPU、OS 和宿主版本的测试不能重复充当不同配置的证据。M0 冻结精确 build 与渠道，M7 增加最近的受支持宿主更新版本回归。

所有“共同核心”用例均须在 P1 至 P4 执行。Windows 和 Mac 只有相同产品目标，不要求相同的系统接口实现。宿主不支持某能力时，应显示 BLOCKED；不能静默将该用例排除出最终完成条件。

### 测试层次

| 层次 | 验证内容 | 可证明的结论 |
| --- | --- | --- |
| 核心自动测试 | 状态、事件顺序、计划版本、操作去重、能力约束 | 新引擎的确定性行为 |
| 适配器契约测试 | 真实宿主的命令、事件、读回结果、保存状态 | 指定宿主版本的接口行为 |
| 真实桌面验收 | 用户操作、原生渲染、浮窗、系统拖放和接收端 | 实际用户流程 |
| 模型回放测试 | 固定模型输出、畸形参数、工具错误和上下文更新 | 模型边界处的引擎行为 |
| 真实模型测试 | 不同 API 配置下的理解、规划和修正 | 指定任务集和模型组合的成功率 |
| 试用验收 | 实际文件和完整用户任务 | 产品可用性和未覆盖问题 |

模拟器不能替代真实宿主、微信或 Mac 设备。核心逻辑可以在 CI 自动验证；桌面和交付用例保留人工验收步骤与可重复证据。明确点击按钮触发的保存和拖放必须在模型断网时也能完成。

## 测试材料

只使用可公开或专门合成的测试文件，真实用户文件由用户选择加入测试。每套材料保存未经修改的基准、生成规则和关键断言。

| 材料 | 内容 | 主要用途 |
| --- | --- | --- |
| F01 基础报告 | 约 10 页文字，3 节正文，标题、编号、基础表格 | 选区、逐段修改和保存交付 |
| F02 复杂报告 | 段落样式、页眉页脚、批注、修订、图片、脚注、公式等 | 修改普通正文时保留无关结构；不支持结构的明确拒绝 |
| F03 销售工作簿 | 两个来源表，已知结果的公式、命名区域、隐藏表和图表 | 汇总正确性、公式保留和宿主重算 |
| F04 汇报演示稿 | 3 页，原生文本框、形状、表格和图表 | 输出可编辑对象及保留其他页面 |
| F05 参考 PDF | 可提取文字与扫描页各一组，约 12 页 | 来源定位及 OCR 能力判断 |
| F06 文件名与大小 | 中文、空格、emoji、组合字符；1 MB、10 MB、50 MB 文件 | 两端路径、拖放和性能 |
| F07 文件身份 | 不同目录中的同名文档、另存为版本、移动后的路径 | 防止目标错绑及关系更新 |
| F08 云端文件 | OneDrive 或 iCloud 的已下载文件与未下载占位文件 | 下载就绪、离线和交付版本 |
| F09 受限文件 | 只读、加密或受保护文档及不可写目录 | 无法操作时的准确状态 |

DOCX/XLSX/PPTX 经宿主保存后可能产生正常的元数据变化。格式保留采用文档对象与规范化结构断言，并辅以原生画面检查，不要求编辑前后 ZIP 二进制完全一致。固定交付副本与目标端下载文件之间则应具有相同字节哈希。

## 成功证据与状态口径

每次动作记录任务身份、计划版本、文档会话、目标文件、操作身份、操作前后的内容摘要或版本、时间和结果。记录应脱敏；API 密钥、认证头和完整敏感内容不进入普通诊断日志。

| 记录状态 | 必须具备的证据 |
| --- | --- |
| 已修改 | 指定宿主执行完成，并读回预期对象内容 |
| 已保存 | 宿主确认保存完成，文件可访问，且对应到指定文档和保存版本 |
| 已准备交付 | 固定副本存在，可读，记录来源保存版本、文件名、大小与哈希 |
| 已发起拖放 | 原生拖放会话真实启动，交付对象为文件 |
| 目标已接收 | 目标应用显示正确附件，或具有可核验的接收记录 |
| 已发送 | 独立观察到正确测试会话中的实际发送结果 |
| 结果待核实 | 动作可能已生效，但尚无法取得可靠结果；不自动重复执行 |

系统拖放回调通常只能证明一次数据传递的结果；不能据此把状态推进到已发送。Windows 使用真实 Shell 文件数据，Mac 使用真实 AppKit 文件拖放。[Windows 文件传输规范](https://learn.microsoft.com/en-us/windows/win32/shell/datascenarios)、[AppKit 文件拖放](https://developer.apple.com/documentation/appkit/drag-and-drop)。

验收证据类型统一为：E1 原生应用与浮窗同屏录像；E2 脱敏动作和事件记录；E3 基准文件、结果文件、交付副本和哈希；E4 文档对象或公式断言；E5 安装、签名、权限与版本记录；E6 性能原始采样；E7 试用任务记录。每个测试至少保留能支持其预期结果的证据。

## 核心工作流程

### J1 在 Word 修改并拖入微信

前置条件：原生文字宿主打开 F01，浮窗绑定此文档；测试者准备专用测试会话。使用 F01 的唯一标记区分每次执行。

1. 用户要求只改第一节，完成后停下检查。
2. Agent 在原生文档中完成修改并定位成果，浮窗等待反馈。
3. 用户手动补充一句话，再要求后续部分改为先写风险和建议。
4. 验证已认可内容与手动补充保留，后续内容按新方向修改。
5. 用户在宿主按 Ctrl+S 或 Command+S。
6. 浮窗显示此次保存状态和正确文件，用户直接从文件卡片拖进微信。
7. 微信显示对应附件。测试者在专用测试会话中手动完成发送，再下载文件核验。
8. 下载文件含唯一标记和手动补充，交付哈希相同，源文档保持打开且内容不丢失。

验收：每个冻结环境单元完成 20 次完整流程，包含改变方向、同名文件和至少 5 次另存为；关键断言全部通过。验证文字宿主时，WPS 使用同等的文字应用操作。录像、动作记录、原文件、交付副本与接收文件建立对应关系。

### J2 未保存文档从浮窗准备交付

1. 在原生应用新建文档，输入唯一标记，不预先保存。
2. 在浮窗选择保存并准备拖出，完成宿主原生另存为流程。
3. 检查文件托盘关联新路径，原文档仍为当前文档。
4. 拖入目标应用并核验文件版本。
5. 分别测试取消另存为、只读目录、磁盘空间不足和云端文件未下载。

验收：成功路径 10 次；每种失败路径 3 次。失败不得生成看似可交付的旧文件，也不得标记为已保存或已接收。每次操作保留源文件与用户已输入内容。

### J3 多文件生成并更新报告

1. 把 F03 的两个来源表与 F05 加入任务，F01 为输出目标。
2. 要求生成第一节总结与汇总表，每个成果均可评价。
3. 核对结果数值、来源范围和跳转位置。
4. 手动更改一个来源表的数值并保存。
5. 检查相关成果标为待复核，要求只更新受影响部分。
6. 准备报告与演示稿两个交付副本，多选拖入目标应用。

验收：每个冻结环境单元 10 次；数值、来源、文件数量和交付版本全部正确。引用文件不被误写，公式没有被无意替换成静态值。

### J4 改方向和崩溃后的恢复

1. 第一段通过检查后，在第二段执行前改变后续方向。
2. 在动作派发前、原生动作生效后但结果写入前、交付副本生成后三个边界分别终止核心进程。
3. 重启并恢复同一任务，核对实际文档和动作记录。
4. 对结果已知的动作续做，对结果不明的动作先核实。
5. 验证没有重复段落、重复附件、旧计划的新写入或用户内容丢失。

验收：三个边界每个环境单元各 3 次。交付或发送结果不明时，不能通过自动重试制造重复副作用。

## 性能与执行次数

### 暂定性能预算

以下数值是产品目标，不是当前测量结果。M0 记录实际硬件和运行时后冻结预算。需要调整时在相关里程碑验收前记录理由与新版本，不通过删除慢样本把失败改成通过。

| 项目 | 暂定预算 | 计时口径 |
| --- | --- | --- |
| 按钮和暂停请求的本地反馈 | P95 不超过 200 ms | 输入事件到明确 UI 状态，不代表原生动作已完成 |
| 已确认保存后的卡片更新 | P95 不超过 1 s | 连接器确认保存完成到卡片显示对应版本 |
| 基础段落修改的原生显示 | P95 不超过 2 s | 有效动作被执行器接受到宿主可见与读回，不含模型生成时间 |
| 本地交付副本准备 | 1 MB 不超过 1 s，10 MB 不超过 2 s，50 MB 不超过 5 s，均按 P95 | 本地 SSD 上的副本创建及完整性确认；云端下载另报 |
| 冷启动至浮窗可交互 | P95 不超过 5 s | 宿主已打开，从启动助手到本地命令可用，不等待模型 |
| 8 小时资源稳定性 | 热身后常驻内存净增长不超过 150 MB，资源数无持续增长 | 只统计助手及其子进程，不含办公应用、微信与外部模型服务 |

普通性能项每个冻结环境单元至少 30 次；P95 采用排序后的向上取整百分位。宿主忙、超时、失败和异常分别记录；失败不能被静默排除出总体成功率。原生动作不可中断时允许保持处理中，禁止在后台仍在写入时提前报告已取消或已失败。

| 场景 | 每个适用环境单元的最少次数 |
| --- | --- |
| M0 最小原生能力实验 | 每项 3 次，宿主重启后再 1 次 |

重复测试使用唯一任务与文件标记，防止缓存结果被误认成本次完成。实际模型测试与固定输出回放分别统计。模型任务的数字计算以已知答案核验，不以另一个模型的主观评分替代。

## 缺陷与放行标准

| 等级 | 例子 | 对发布的影响 |
| --- | --- | --- |
| S0 | 原文件损坏、不可恢复的内容丢失、敏感凭据泄漏、未经指定发送到错误对象 | 立即阻断全部相关发布，修复后复核同类路径 |
| S1 | 改错文档、覆盖用户手改、交付旧版本、重复副作用、关键流程无法完成、假报完成 | 对应阶段与平台不可放行 |
| S2 | 不影响内容正确性的性能或易用性问题 | 记录范围、缓解办法和计划，不能降低关键成功断言 |
| S3 | 文案、轻微视觉或低频便利性问题 | 可进入待办，不影响当前操作的准确理解 |

阶段放行需指定用例执行完毕、关键断言 100% 通过、S0/S1 缺陷为零，并具备实际版本和证据。SKIPPED、NOT_RUN、BLOCKED 不能计为通过；不适用项须有已同意的支持范围依据。

M8 还需四组合及其冻结 OS 子配置全部满足 J1 至 J4 和相关核心用例，真实模型有效任务成功率至少 95%，试用成功率至少 95%。关键的数据保留、目标绑定、交付版本和不重复副作用断言仍须 100% 通过。

M0 的能力验证、M2 的真实文件交付和 M7 的正式安装分别需要独立证据。P4 若受接口限制而无法完成，最终四组合验收保持阻塞；其他配置成功不会自动改变这一结论。

## 证据目录和执行记录模板

执行时按 `release / environment / case / run` 建立证据目录。每个环境附版本清单，每次运行使用唯一编号。规划阶段的用例保持 NOT_RUN，执行时创建实际证据和记录。

| 字段 | 填写内容 |
| --- | --- |
| 用例 | 例如 DRAG-01，关联 M2 和 M6 |
| 环境 | P 配置、OS build、CPU、宿主版本与渠道、微信版本 |
| 软件版本 | 助手与连接器构建标识、运行时锁定版本 |
| API 配置 | 服务商、模型版本与能力，不记录密钥 |
| 前置材料 | 材料编号、原文件哈希、任务唯一标记 |
| 执行步骤 | 实际操作、失败注入位置、时间与执行人 |
| 预期和实际 | 分别填写，不能只写模型回答 |
| 状态 | NOT_RUN、PASS、FAIL、BLOCKED 或经解释的 SKIPPED |
| 证据 | E1 至 E7 对应文件位置或可访问引用 |
| 问题 | 缺陷编号、等级、复现方式与修复版本 |
| 复测 | 保留原失败记录，追加新的完整测试结果 |

本轮交付为规划和验收定义。只有未来真实执行后的记录，才可将某个环境、用例或里程碑标为已验收。
